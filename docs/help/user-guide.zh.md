# MFA-Forge 用户指南

## 概览
MFA-Forge 是一个面向 Windows 的本地优先 MFA 管理器。它的核心目标是把 TOTP 账户保存在加密保险库中，并在 GUI、人工 CLI、本地代理会话和 MCP 服务器之间提供一致的工作流。应用的设计重点是让密钥始终留在本机、让敏感操作保持显式确认、并避免自动化静默绕过 unlock 与 grant 边界。

## 开始使用
首次启动时，你必须创建主密码。这个主密码就是保险库的主钥匙。没有它，你无法添加账户、导入 seed、导出备份、轮换密码，也无法生成代码。

输入主密码之后，MFA-Forge 还会执行这一条发布线使用的额外 Windows 验证流程。实际使用中，只有这两个步骤都成功后，应用才真正处于可用状态。

解锁后，主窗口分为三个工作区域：

- 左侧的 workspace 树
- 中间的账户列表
- 覆盖在该布局上的上下文操作和对话框

这种结构的目的是让你先选定范围，再在当前范围内操作，而不是频繁切换到其他界面。

## Workspaces
Workspace 是账户分组系统。你可以用它按项目、客户、环境或团队来组织 token。

它的工作方式：

- 根 workspace 是顶层容器
- 子目录是某个已有 workspace 下的嵌套路径
- 账户既可以放在 workspace 路径内，也可以保持未分配

它的重要性：

- 当前激活的 workspace 会过滤账户视图
- 新建账户默认继承当前选中的 workspace
- 当账户组织得一致时，导出、恢复和审查操作会更清晰

如果你有个人账户或应急账户，把它们保留为未分配状态会比较方便。

## 添加账户
MFA-Forge 支持四种主要方式来加载 TOTP 账户：

1. 手动录入
2. 导入 `otpauth://` URI
3. 导入 QR 图片
4. 导入兼容文件

当你希望直接控制 service、user、workspace、algorithm、digits 和 period 时，手动录入最合适。

如果其他系统已经以标准 TOTP 格式给了你 seed，那么 URI、QR 或文件导入会更方便。MFA-Forge 会解析来源、提取账户字段，并把 secret 以加密方式保存到保险库中。

重要行为：

- secret 在界面中始终保持遮罩
- 导入对话框关闭时会清理敏感文本
- 修改 metadata 不要求同时修改 secret
- 修改 secret 是可选的；如果该字段留空，就会保留当前已加密的 secret

## 令牌与历史
Token 窗口是读取验证码的操作视图。当你从某一行账户打开它时，MFA-Forge 会从已解锁的保险库读取当前 TOTP 值，并显示当前周期的倒计时。

刷新时应当理解的行为：

- 如果当前 TOTP 周期还没有结束，刷新后返回相同代码是正常现象
- 如果周期已经切换，界面中的代码会立即更新
- 复制操作只会复制当前 token，不会复制 secret

History 的用途不同。它不是用来读取 token，而是用来恢复状态。

Restore 对话框允许你：

- 查看可恢复的快照
- 恢复被删除的账户
- 把某个之前可见的版本恢复回当前保险库

当账户被误删、metadata 被错误修改，或者你希望回到之前版本而不想手动重建账户时，应当使用 history。

## 备份与导入
Export 会创建加密的 MFA-Forge 备份文件。它的目的是把整个保险库保存成以后可以再次由 MFA-Forge 导入的格式。

Import 的效果被故意设计得比较强：在验证通过后，它会用导入的加密备份替换当前保险库内容。这适合灾难恢复或机器迁移，但应把它理解为受控恢复操作，而不是合并。

推荐做法：

- 在大改动或批量导入之前先创建备份
- 将备份保存在受保护的位置
- 在应用之前确认你导入的确实是预期中的备份

## 本地代理与 MCP
本地代理会话和 MCP 服务器是为本地自动化准备的，但它们并不是永久可信通道。

核心行为：

- 两者都从 `deny-by-default` 状态启动
- 打开会话必须经过原生 unlock 流程
- 已解锁会话只在进程存活期间有效
- 敏感操作需要显式 grant 或专门的 prompt

受保护操作的示例：

- 为某个账户生成 token
- provision 或导入账户
- 读取敏感历史或审计数据
- 轮换主密码

这意味着自动化是可行的，但它始终受限于用户明确批准以及本地会话生命周期。

## 故障排除
如果 unlock 失败：

- 先确认主密码是否正确
- 然后完成出现的 Windows 验证提示
- 如果应用又回到 loader，请重新尝试，并注意主窗口之外是否弹出了原生提示

如果导入失败：

- 检查来源是否仍然包含有效的 `otpauth://` payload
- 检查 Base32 secret 是否完整
- 检查所选 QR 图片是否确实对应预期的 seed

如果 token 看起来没有变化：

- 先看当前 TOTP 周期还剩多少秒
- 等周期切换后再刷新一次

如果自动化被拒绝：

- 检查会话是否仍然打开
- 检查所需 grant 是否已经过期或被消耗
- 必要时重新打开本地会话，并重新批准那一个精确操作
